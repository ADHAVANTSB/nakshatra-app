## 2. Scope & methodology

- **Target**: `nakshatra-app` only. `Code.gs`, `appsscript.json`, backend tests, DB
  schema and deployment settings were not modified. No commits, pushes or PRs.
- **Strategy**: `ng serve` (local dev server) + Playwright route interception. Every
  request to the production Apps Script endpoint
  (`https://script.google.com/macros/s/AKfycbw3…/exec`) is stubbed; any action the stub
  does not explicitly know is **aborted at the network layer** — the suite can never
  leak to production and can never fabricate a passing result from an unexpected
  response.
- **Sign-in**: the Google Identity Services script (`accounts.google.com/gsi/client`) is
  served by a local stub; tests click the rendered button and a crafted test credential
  is delivered to the app's callback. Real OAuth is never exercised (labelled MOCKED).
- **Dependencies added**: `@playwright/test` (Chromium only), `axe-core` (injected raw
  via `page.addScriptTag` — no wrapper package). Both dev-only.
- **New harness files**: `playwright.config.ts` (3 projects: desktop-chromium 1280px,
  mobile-chromium Pixel 7 emulation, tablet-chromium 768×1024 touch), `e2e/fixtures.ts`,
  `e2e/stubs/backend.ts`, and seven spec files under `e2e/journeys/`.
- **Trace-driven debugging**: failures were diagnosed from Playwright traces (network
  payloads + console errors), not guesswork.

## 4. Defects found & fixed (with evidence)

### Functional defect 1 — session-restore race on boot
- **Symptom**: a fast `validateSession` response could beat the auth guard's boot
  redirect to `/#/login`, leaving a *validated* user stranded on the login card.
- **Evidence**: trace of the "restores a persisted session" journey showed the dashboard
  render followed by a re-render of the sign-in card.
- **Fix** (`app.ts`): `validateStartupSession` now tracks `restoredFromStorage` and
  navigates to `/dashboard` when the user is restored (or already on the login route).
- **Regression pinned**: updated `app.spec.ts`; E2E A-05/A-06 journeys cover refresh on
  `/dashboard` and refresh on `/#/login`.

### Functional defect 2 — archive lifecycle unreachable with zero active homes
- **Symptom**: the archive-lifecycle UI (notice, preview dialog, "Archived homes" /
  Restore section) was nested inside the non-empty `@else` branch of the homes list, so
  when **all** homes were archived the Restore path was impossible to reach.
- **Evidence**: E2E archive journey hung at the restore step with an empty active list.
- **Fix** (`homes.html`): moved the block out of the `@else` branch. Prettier run;
  `tsc` clean; 164 unit tests green; E2E restore-from-empty journey passes.

### Accessibility defects (found by the axe smoke + fixed)
1. **aria-hidden focusable control**: the sidebar toggle checkbox was `aria-hidden` yet
   focusable — fixed (removed `aria-hidden`, added `tabindex="-1"` + `aria-label`).
   (`aria-hidden-focus`, serious)
2. **Prohibited attribute**: both toggles put `aria-label` on `<label>` elements —
   removed. (`aria-prohibited-attr`, serious)
3. **Name/visible-text mismatch**: the header account button's static `aria-label`
   could not contain its visible text (avatar + name + role chip), tripping
   `label-content-name-mismatch` (serious) — fixed by removing the label so the button
   is named by its content; `aria-expanded` still conveys menu state.
4. **Missing accessible names (critical)**: four bare `<select>` filters on the events
   page had no accessible name — `aria-label`s added. (`select-name`)
5. **Color contrast (serious, app-wide)**: the muted-text palette failed WCAG AA on
   white (2.7–4.5:1). Systematic fixes, palette-consistent:
   `--nk-muted #8aa0b0 → #58707f`, `--nk-muted-light #9aadb8 → #58707f`,
   `--nk-primary-dark #087da9 → #066a8c`, `#6f8297 → #58707f`,
   `#817973/#8b827c → #6e6158`, `#817873 → #6e6158`, `#8a93a3 → #58707f`,
   `#087caf → #066a8c`, footer brand `#159ed0 → #0d7ba4`, attendance
   present/absent chips & buttons and table headers darkened. Only text colors were
   darkened; layout untouched.

## 5. Accessibility findings — smoke, not compliance

The axe-core smoke (critical + serious rules = failure) now passes on login, dashboard,
homes, participants, events and attendance in the desktop project. **This is a smoke
signal, not a WCAG conformance claim**: it covers six routes, one browser engine
(Chromium), and emulated viewports only. Keyboard-only walks, screen-reader testing,
zoom/reflow and cognitive review remain manual work (the `verification-before-completion`
principle applies: no compliance claim is made beyond what was executed).

## 6. Responsive & emulation results

- Desktop (1280px), tablet (768×1024, touch) and mobile (Pixel 7 emulation) sweeps found
  **no horizontal overflow** on the swept routes.
- The mobile navigation drawer journey (open → navigate → lands on section) passes.
- **Caveat**: these are *emulated* viewports and touch/hover behaviors in Chromium — real
  Android/iOS devices may still differ. No physical-device testing was performed; none
  is claimed.
- Test assertions were made viewport-aware (drawer vs. sidebar navigation) rather than
  loosened, so the same journey asserts the same contract on every project.

## 8. Risks & observations

- **H-02 nuance**: on dashboard/homes, a failed read *replaces* the content with an
  error + Retry instead of showing stale figures alongside the error. This is the
  established design (no fabricated or blank data; the session is never dropped) and
  the E2E suite asserts that exact contract. If stakeholders prefer "stale data +
  banner", that is a product decision, not a defect fix.
- **Error honesty verified**: HTTP 404 HTML pages, malformed envelopes, aborted requests
  and backend rejections never produce success messages; backend error strings are
  surfaced verbatim (including the pinned messages, e.g. "Google Sheet updated.").
- **E2E-only gotchas handled**: success toasts accumulate (count-based assertions);
  route priority ensures the stub, not production, answers; the abort catch-all is
  registered first.
- `.gitignore` now excludes `test-results/` and `playwright-report/` (Playwright
  artifacts). `deploy-pages.yml` was not touched.

## 9. Verdict

The frontend passes every executable gate in this environment: 164/164 unit tests, a
clean production build and type-check, and 124 passing E2E executions (0 failures)
across desktop/tablet/mobile emulation, including an honest-error and
accessibility-smoke layer that did not exist before this pass. The remaining risk is
concentrated in live-backend behaviors (real OAuth, real Sheets sync, Sync-All job,
user management), which are **explicitly blocked, not silently omitted**. Recommended
next step: stand up a non-production Apps Script deployment + disposable test
spreadsheet to convert the blocked/not-run items into automated coverage, and schedule
the manual accessibility review for a formal WCAG statement.
